# 浏览器内部录制实验

## 结论

浏览器内部录制是可行的研究方向，但 **1.7.0 尚未使用它录云原神**。
本版仍使用 macOS 的独立窗口捕获：窗口不必置顶，自动点击则仍需确认
目标窗口和点击位置未被遮挡。录制和输入的安全条件不是同一件事。

## 实际测了什么

在独立 Chrome 配置中播放带逐帧计数和测试音的合成视频，分别录制
`video.captureStream()` 和视频源 `MediaStream` 的副本。使用 H.264/AAC
生成两份约 21 秒 MP4，在中间用原生不透明窗口完全盖住浏览器 12 秒，
并切走应用焦点。测试框架关闭默认焦点模拟；页面实际报告 hidden 和 blur。

两份成片分别逐帧解码 635、636 帧，源帧计数没有倒退或跳过超过一帧，
最大视频时间间隔约 0.037 秒；每秒都有非静音测试音，严格解码无错误。
桌面截图中的遮挡层覆盖超过 99%，成片没有该遮挡层。实验也暴露了
WebM/Opus 组合的解码错误，因此不能把所有浏览器编码配置都视为通过。

**没有通过的边界：** 测试通知没有实际显示出系统横幅，因此不能称
“真实通知横幅实测通过”。本次没有登录游戏，没有验证远程 WebRTC、
Safari、真实云游戏声音、长时间后台运行或游戏断线重连。完整遮挡测试
比一张通知覆盖范围更大，但不能替代系统通知生命周期或真实游戏验收。
测试素材、浏览器配置和桌面截图不随应用发布。

## 为什么不能直接替换现有录屏

- [Chrome tabCapture](https://developer.chrome.com/docs/extensions/reference/api/tabCapture)
  可以采集标签页音视频，但需要扩展和用户操作，不能直接复用于 Safari。
- [媒体元素 captureStream](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/captureStream)
  并非所有浏览器都支持。复制已有媒体流是另一条路线，但需要页面确实
  暴露可访问的流，还要处理音频、画布、替换轨道和重连。
- [浏览器屏幕采集](https://developer.chrome.com/docs/extensions/how-to/web-platform/screen-capture)
  的目标选择、用户同意和扩展后台生命周期也不同，不能绕过系统授权。

下一步应在明确允许的真实云游戏会话上验证：完整画面和音轨、通知横幅、
失焦/隐藏、窗口缩放、流重连，以及逐帧和声音连续性。通过这些检查后，
才适合提供独立的浏览器录制选项，而不是静默更换录制后端。
